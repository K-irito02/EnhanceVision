## 🔴 严重 Bug（崩溃/数据丢失/资源泄漏）

### S-01: TaskSwitchSynchronizer 双重互斥锁竞态

**文件**: `include/EnhanceVision/controllers/ProcessingController.h:53-84`  
**问题描述**: `TaskSwitchSynchronizer` 同时使用 `QMutex m_mutex` 和 `std::mutex m_switchMutex` 保护相关状态，但 `beginTaskSwitch()`/`endTaskSwitch()` 用 `QMutex`，而 `waitForSwitchComplete()` 用 `std::mutex`。两个锁保护同一数据 `m_currentSwitch`，但访问路径不一致——`waitForSwitchComplete()` 读取 `m_currentSwitch.oldTaskId` 时未持有 `QMutex`，而 `endTaskSwitch()` 修改 `m_currentSwitch` 时持有 `QMutex`，形成数据竞态。  
**影响范围**: 任务切换时可能读到半写入的 `SwitchInfo`，导致条件变量永远不被唤醒（死锁）或错误唤醒。  
**修复建议**: 统一使用同一把锁（推荐 `std::mutex`），或让 `waitForSwitchComplete()` 也获取 `QMutex`。

### S-02: AIInferenceWorker::requestCancel() — m_cancelReason 无线程安全保护

**文件**: `src/core/ai/AIInferenceWorker.cpp:81-89`  
**问题描述**: `requestCancel()` 设置 `m_cancelReason = reason`（普通成员变量，非 `std::atomic`），但 `m_cancelRequested` 和 `m_forceCancel` 是 `std::atomic`。`requestCancel()` 可从任意线程调用，而 `startTask()` 在工作线程读取 `m_cancelReason`，存在数据竞态。  
**影响范围**: 取消原因可能被覆盖或读到半写入值，导致错误日志或错误恢复行为。  
**修复建议**: 将 `m_cancelReason` 改为 `std::atomic<int>`，或在 `requestCancel()` 和读取处加 `QMutexLocker`。

### S-03: AIInferenceWorker::setState() — m_currentTaskId 无锁读取

**文件**: `src/core/ai/AIInferenceWorker.cpp:179-187`  
**问题描述**: `setState()` 在 `m_mutex` 未锁定的情况下读取 `m_currentTaskId` 来 emit 信号。`m_currentTaskId` 的写入在 `startTask()` 中受 `m_mutex` 保护，但 `setState()` 不获取锁就读取，构成数据竞态。  
**影响范围**: 信号可能携带空或错误的 taskId，导致上层控制器状态混乱。  
**修复建议**: 在 `setState()` 中加 `QMutexLocker locker(&m_mutex)` 读取 `m_currentTaskId`，或将 taskId 作为参数传入 `setState()`。

### S-04: AIInferenceWorker::waitForCompletion() — 条件变量与状态检查的竞态

**文件**: `src/core/ai/AIInferenceWorker.cpp:131-140`  
**问题描述**: `waitForCompletion()` 使用 `m_completionMutex` 等待，但 `startTask()` 中的 `m_completionCondition.wakeAll()` 可能在 `setState()` 将状态从 Processing 转换为 Completed/Failed 之前执行。如果 `waitForCompletion()` 在 `wakeAll()` 之后、`setState()` 之前被调用，`isProcessing()` 返回 true 但条件变量已被唤醒，导致虚假返回。  
**影响范围**: 调用方可能误判任务已完成，但实际状态尚未更新。  
**修复建议**: 在 `startTask()` 中，先 `setState()` 再 `wakeAll()`，或在 `waitForCompletion()` 中使用谓词循环等待 `!isProcessing()`。

### S-05: AITaskQueue::enqueue() — 信号在锁外发射但 queueSizeChanged 读取无锁

**文件**: `src/core/ai/AITaskQueue.cpp:56-57`  
**问题描述**: `enqueue()` 在释放 `m_mutex` 后 emit `queueSizeChanged(static_cast<int>(m_queue.size()))`，但此时 `m_queue.size()` 的读取没有锁保护，其他线程可能同时修改队列，导致 size 值不准确。  
**影响范围**: 信号携带的队列大小可能不准确，UI 显示不一致。  
**修复建议**: 在锁内计算 size，存入局部变量，锁外 emit 局部变量值。

### S-06: ImagePostprocessor::applyInverseTTATransform() — TTA 逆变换未实现

**文件**: `src/core/inference/ImagePostprocessor.cpp:122-126`  
**问题描述**: `applyInverseTTATransform()` 忽略 `transformIndex` 参数，对所有变换统一只做 `mirrored(false, true)`（垂直翻转），完全没有实现 8 种 TTA 逆变换。这意味着 TTA 模式产生的结果完全错误——除了原始图像和垂直翻转外，其他 6 种变换的逆变换都不正确。  
**影响范围**: 使用 TTA 模式时，推理结果图像质量严重下降，合并结果完全错误。这是功能性 Bug。  
**修复建议**: 根据 `transformIndex` 实现完整的 8 种逆变换：0-无操作，1-水平翻转，2-垂直翻转，3-双翻转，4-7-旋转+翻转组合。

### S-07: NCNNVulkanBackend::runInference() — 推理期间持有 m_mutex 导致死锁风险

**文件**: `src/core/inference/NCNNVulkanBackend.cpp:589`  
**问题描述**: `runInference()` 在第 589 行获取 `QMutexLocker netLocker(&m_mutex)`，整个推理过程（包括 `ex.input()` 和 `ex.extract()`）都在锁内执行。而 `loadModel()` 也需要 `m_mutex`（第 203 行），`shutdown()` 也需要 `m_mutex`（第 126 行）。如果推理耗时较长，取消操作调用 `shutdown()` 或 `loadModel()` 将被阻塞，无法及时响应。更严重的是，如果 `inference()` 持有 `m_inferenceMutex` + `m_mutex`，而另一个线程先获取 `m_mutex` 再获取 `m_inferenceMutex`，可能死锁。  
**影响范围**: 推理期间无法取消或切换模型，UI 可能卡死。  
**修复建议**: 缩小 `m_mutex` 的锁定范围——仅在创建 Extractor 和设置输入时持锁，实际推理（extract）期间释放锁。或使用读写锁（`QReadWriteLock`），推理用读锁，模型加载用写锁。

### S-08: AIEnginePool::release() — lambda 捕获后析构竞态

**文件**: `src/core/AIEnginePool.cpp:176-185`  
**问题描述**: `release()` 中连接 `processingCancelled` 信号的 lambda 捕获了 `idx` 和 `taskId`（值拷贝），但 lambda 内部再次获取 `m_mutex`。如果 `destroyEngines()` 在信号触发前被调用（析构时），`m_slots[idx]` 可能已不存在，导致越界访问。虽然 `destroyEngines()` 先调用 `cancelProcess()`，但信号是 `Qt::QueuedConnection`，可能在 `destroyEngines()` 完成后才触发。  
**影响范围**: 程序退出时可能崩溃——lambda 在对象析构后触发，访问已释放的 `m_slots`。  
**修复建议**: 在 `destroyEngines()` 中断开所有信号连接，或使用 `QPointer` 检查对象是否仍然有效，或在 lambda 中验证 `idx < m_slots.size()`。

### S-09: TaskCoordinator 持锁 emit 信号 — 潜在死锁

**文件**: `src/core/TaskCoordinator.cpp:27-43, 73-101, 135-156`  
**问题描述**: `registerTask()`、`unregisterTask()`、`cancelMessageTasks()`、`cancelSessionTasks()`、`cancelTask()`、`updateTaskState()`、`markMessageOrphaned()`、`markSessionOrphaned()` 等方法均在持有 `m_mutex` 的情况下 emit 信号。如果信号接收者在槽函数中也尝试获取 `m_mutex`（直接或间接），将导致死锁。  
**影响范围**: 任何在 TaskCoordinator 信号槽连接中回调 TaskCoordinator 方法的场景都可能死锁。  
**修复建议**: 在 emit 信号前释放锁（先拷贝数据到局部变量，unlocker 后 emit），或确保所有连接使用 `Qt::QueuedConnection`。

### S-10: ResourceManager::tryAcquire()/release() 无线程安全保护

**文件**: `src/core/ResourceManager.cpp:50-63`  
**问题描述**: `tryAcquire()` 和 `release()` 操作 `m_taskResources`（`QHash`），但没有任何 mutex 保护。`canStartNewTask()` 调用 `usedMemoryMB()` 和 `usedGpuMemoryMB()` 遍历 `m_taskResources`，而其他线程可能同时调用 `release()` 修改该容器。`QHash` 不是线程安全的，并发读写可能导致崩溃。  
**影响范围**: 多线程并发请求/释放资源时可能崩溃或配额越界。  
**修复建议**: 为 `m_taskResources` 添加 `QMutex` 保护，或将 ResourceManager 的所有公共方法加锁。

### S-11: LifecycleSupervisor::armForceTerminate() — detached 线程访问可能已析构的 this

**文件**: `src/core/LifecycleSupervisor.cpp:335-356`  
**问题描述**: `armForceTerminate()` 创建 `std::thread` 并 detach，线程内访问 `m_forceTerminateArmed`、`m_forceTerminateGeneration` 和调用 `forceTerminate()`。如果 `LifecycleSupervisor` 对象在 detach 线程执行前被析构，这些访问将是未定义行为。虽然 `forceTerminate()` 最终调用 `TerminateProcess`，但在到达之前访问已析构对象的成员变量可能导致崩溃。  
**影响范围**: 应用退出流程中，如果 `LifecycleSupervisor` 析构时机不当，可能触发崩溃。  
**修复建议**: 将 atomic 变量改为全局/静态变量，或在析构函数中等待 detach 线程完成（使用 `std::promise`/`std::future` 或 joinable thread）。

### S-12: QML ShaderParamsPanel 属性绑定断裂 — 滑块调整后 C++ 侧变更无法回传

**文件**: `qml/components/ShaderParamsPanel.qml:14-27`, `qml/components/ControlPanel.qml:35-48`  
**问题描述**: `ShaderParamsPanel` 的 14 个 Shader 参数初始绑定为 `UIStateController.xxx`。当用户拖动 ParamSlider 时，`onParamValueChanged` 执行 `root.brightness = newValue`，这直接打破了 `property real brightness: UIStateController.brightness` 的绑定。此后如果 C++ 侧通过其他途径修改了 `UIStateController.brightness`（如切换会话、恢复状态），QML 层将无法感知变更，UI 与实际状态永久脱节。  
**影响范围**: 所有 Shader 参数调节，涉及核心编辑流程。用户调参后切换会话或恢复状态，滑块和预览不会更新。  
**修复建议**: 不要直接赋值 `root.brightness = newValue`，改为仅调用 `root.updateParam("brightness", newValue)`，让 `UIStateController` 的属性变更信号自动驱动绑定更新。或使用 `Qt.binding()` 在赋值后重新建立绑定。

### S-13: App.qml 中 sidebarExpanded/controlPanelCollapsed/sidebarWidth 绑定断裂

**文件**: `qml/App.qml:22-29`, `qml/App.qml:96-101`, `qml/App.qml:164-168`  
**问题描述**: `App.qml` 中 `sidebarExpanded`、`controlPanelCollapsed`、`sidebarWidth` 初始绑定为 `UIStateController.xxx`。但在 TitleBar 和 Sidebar 的信号处理器中，先执行 `root.sidebarExpanded = !root.sidebarExpanded`（打破绑定），再执行 `UIStateController.sidebarExpanded = root.sidebarExpanded`。绑定断裂后，后续 C++ 侧的变更无法传播到 QML。  
**影响范围**: 侧边栏展开/收缩、控制面板折叠、侧边栏宽度拖拽调整。如果 C++ 侧因恢复状态改变了这些值，UI 不会同步。  
**修复建议**: 只修改 `UIStateController` 的值，让绑定自动同步：`UIStateController.sidebarExpanded = !UIStateController.sidebarExpanded`。

### S-14: fullshader.frag 中 blur 采样源不一致 — 中心像素用处理后颜色，邻域像素用原始纹理

**文件**: `resources/shaders/fullshader.frag:159-181`  
**问题描述**: blur 实现中，中心像素使用已处理的 `rgb` 值（`blurColor = rgb * weights[0]`），但邻域像素直接从 `source` 纹理采样（`texture(source, ...)`）。这意味着中心像素是经过 brightness/contrast/saturation 等调整后的颜色，而邻域像素是原始颜色。两者混合后会产生不自然的色差，特别是在高对比度或强色调调整时尤为明显。  
**影响范围**: 所有使用 blur 效果的 Shader 处理，blur 与其他参数组合使用时效果异常。  
**修复建议**: 方案一：将 blur 移到所有颜色调整之前执行（先 blur 后调色）；方案二：使用两遍渲染（先渲染颜色调整到 FBO，再对 FBO 做 blur）。

### S-15: OffscreenShaderRenderer 导出无修改图像时 grabToImage 返回空

**文件**: `qml/components/OffscreenShaderRenderer.qml:61-81`, `qml/components/FullShaderEffect.qml`  
**问题描述**: `OffscreenShaderRenderer` 使用 `FullShaderEffect` 进行渲染，但 `FullShaderEffect` 的 `visible` 属性受 `hasModifications` 控制。当所有 Shader 参数为默认值时，`hasModifications` 为 `false`，`FullShaderEffect` 不可见。此时 `grabToImage()` 在不可见的 ShaderEffect 上调用，会返回空/透明图像，导致导出失败。  
**影响范围**: 用户在未修改任何 Shader 参数时点击导出，将得到空白图片。  
**修复建议**: 当 `hasModifications` 为 `false` 时，直接对 `sourceImage` 调用 `grabToImage()` 而非对 `shaderEffect` 调用。或在导出时强制设置 `shaderEffect.visible = true`。

### S-16: Dialog 点击背景关闭不触发回调，导致 NotificationManager 状态泄漏

**文件**: `qml/components/Dialog.qml:93-101`, `qml/utils/NotificationManager.qml:69-94`  
**问题描述**: `Dialog.qml` 中背景遮罩的 `MouseArea.onClicked` 调用 `root.hide()`，但 `hide()` 只触发 `closed()` 信号，不触发 `primaryButtonClicked()` 或 `secondaryButtonClicked()`。而 `NotificationManager.showConfirmDialog()` 注册了 `_confirmCallback` 和 `_cancelCallback`，如果用户点击背景关闭对话框，两个回调都不会被调用，回调永远不会被清理。  
**影响范围**: 所有确认对话框（如缓存清理确认、模式切换拦截等）。回调未执行可能导致业务逻辑中断（如任务未取消、状态未回滚）。  
**修复建议**: 在 `Dialog.hide()` 或 `closed()` 信号中，如果对话框类型是 Confirm，自动调用 `secondaryButtonClicked()`（等同于取消）。或在 `NotificationManager` 中监听 `closed()` 信号清理回调。

## 🟡 中等 Bug（逻辑错误/状态不一致）

### M-01: ProcessingController::processNextTask() — 恢复暂停视频处理器时 m_currentProcessingCount 重复递增

**文件**: `src/controllers/ProcessingController.cpp:993-995`  
**问题描述**: 在模式 0/2 的优先恢复逻辑中，当恢复暂停的视频处理器时，代码执行 `m_currentProcessingCount++`。但 `processNextTask()` 开头有 `if (m_currentProcessingCount >= 1) return;` 的检查。如果当前已有任务在处理，恢复逻辑永远不会执行到；如果 `m_currentProcessingCount == 0`，恢复暂停的视频处理器会递增计数到 1，导致队列不再调度新任务。  
**影响范围**: 暂停/恢复视频处理时，队列调度可能卡住或计数不一致。  
**修复建议**: 恢复暂停的视频处理器不应递增 `m_currentProcessingCount`（因为它之前已经被计入）。

### M-02: TaskRecoveryController::applyRecoverableStateToSessions() — 修改消息副本而非引用

**文件**: `src/controllers/TaskRecoveryController.cpp:519-545`  
**问题描述**: 第 519 行 `Message message;` 创建了一个新的局部消息对象，后续对 `message.status` 的修改直接覆盖为 `Recoverable`，没有考虑部分文件已经是 Completed 的情况。  
**影响范围**: 恢复后消息状态可能不正确——如果消息中部分文件已完成、部分需要恢复，整体状态被强制设为 Recoverable。  
**修复建议**: 使用 `recomputeMessageStatus()` 函数来计算消息状态，而非直接赋值 `Recoverable`。

### M-03: SessionController::saveSessions() — 异步保存期间数据竞态

**文件**: `src/controllers/SessionController.cpp:826-861`  
**问题描述**: `saveSessions()` 在主线程构建 `QJsonObject root`，然后通过 `QtConcurrent::run()` 在后台线程写入文件。`root` 是按值捕获的（快照），但 `m_saveInProgress` 标志在后台线程完成后的 `QMetaObject::invokeMethod` 中重置，而主线程可能在此期间继续修改会话数据并调用 `saveSessions()`，此时 `m_saveInProgress == true` 会导致 `m_saveQueued = true`，但队列中只有一个保存机会，中间的修改可能丢失。  
**影响范围**: 快速连续修改会话时，部分修改可能不被持久化。  
**修复建议**: 当 `m_saveQueued` 触发保存时，重新构建 JSON 快照而非使用旧的。

### M-04: VideoFrameBuffer::clear() — m_stopped 标志不可重置

**文件**: `src/core/video/VideoFrameBuffer.cpp:124-131`  
**问题描述**: `clear()` 将 `m_stopped` 设为 `true`，但没有方法将其重置为 `false`。一旦调用 `clear()`，`pushFrame()` 和 `popFrame()` 将永远返回 `false`，缓冲区永久失效。  
**影响范围**: 缓冲区不可复用，如果调用方不知道 `clear()` 的不可逆性，可能在后续 `pushFrame()` 时静默丢失帧。  
**修复建议**: 添加 `reset()` 方法将 `m_stopped` 重置为 `false`，或在 `clear()` 中不设置 `m_stopped`。

### M-05: AIVideoProcessor::processInternal() — fflush(stdout) 调用冗余且可能阻塞

**文件**: `src/core/video/AIVideoProcessor.cpp:356-369`  
**问题描述**: 视频处理循环中大量调用 `fflush(stdout)`（约 10+ 处），这在 Windows 上可能阻塞，尤其是当 stdout 被重定向到管道或文件时。在帧处理热路径中调用 `fflush()` 会显著降低视频处理性能。  
**影响范围**: 视频处理性能下降，特别是在 Windows 上 stdout 被重定向时。  
**修复建议**: 移除所有 `fflush(stdout)` 调用，使用 `qDebug()` 等 Qt 日志系统。

### M-06: NCNNVulkanBackend::probeDevice() — Vulkan 实例泄漏

**文件**: `src/core/inference/NCNNVulkanBackend.cpp:57-96`  
**问题描述**: `probeDevice()` 调用 `ncnn::create_gpu_instance()` 成功后，在获取 GPU 信息后调用 `ncnn::destroy_gpu_instance()`。但如果在 `get_gpu_info()` 抛出异常时（第 85 行 catch），`destroy_gpu_instance()` 不会被调用，导致 Vulkan 实例泄漏。  
**影响范围**: Vulkan GPU 实例泄漏，可能导致后续初始化失败或 GPU 资源耗尽。  
**修复建议**: 使用 RAII 包装器或在 catch 块中也调用 `ncnn::destroy_gpu_instance()`。

### M-07: AIEnginePool::availableCount() — 无锁遍历 m_slots

**文件**: `src/core/AIEnginePool.cpp:228-246`  
**问题描述**: `availableCount()` 未获取 `m_mutex` 就遍历 `m_slots`，而 `m_slots` 可能被其他线程修改（如 `release()`、`acquire()` 等）。虽然 `EngineState` 是枚举值读取通常是原子的，但 `m_slots` 容器本身不是线程安全的——其他线程可能正在 `append()` 或 `removeAt()`。  
**影响范围**: 并发调用时可能读到不一致的槽位状态或越界访问。  
**修复建议**: 在 `availableCount()` 中加 `QMutexLocker locker(&m_mutex)`。

### M-08: ProcessingController Q_PROPERTY resourcePressure NOTIFY 信号冗余发射

**文件**: `include/EnhanceVision/controllers/ProcessingController.h:111`, `src/controllers/ProcessingController.cpp:3227-3237`  
**问题描述**: `resourcePressureChanged()` 信号在 `onResourcePressureChanged` 回调中发射，但不检查 `m_resourcePressure` 值是否真的改变了——如果 ResourceManager 发送了相同 pressure level，会重复 emit，触发不必要的 `pauseQueue()`/`resumeQueue()` 调用。  
**影响范围**: QML 绑定可能收到冗余通知，或资源压力自动暂停/恢复逻辑重复触发。  
**修复建议**: 在 `onResourcePressureChanged` 中检查 `m_resourcePressure != pressureLevel` 再更新和 emit。

### M-09: AutoSaveService::autoSaveResult() — 后台线程 emit 信号

**文件**: `src/services/AutoSaveService.cpp:79-101`  
**问题描述**: `autoSaveResult()` 通过 `QThreadPool::globalInstance()->start()` 在后台线程执行文件复制，完成后在后台线程直接 emit `autoSaveCompleted` 信号。如果接收者在主线程，默认的 `AutoConnection` 会变为 `QueuedConnection`，但如果接收者在同一个线程池中，可能导致线程安全问题。  
**影响范围**: 信号接收者可能不在主线程执行，导致 UI 更新或状态修改的线程安全问题。  
**修复建议**: 使用 `QMetaObject::invokeMethod` 在主线程 emit 信号，或确保所有连接使用 `Qt::QueuedConnection`。

### M-10: Toast 外层 MouseArea 拦截关闭按钮点击

**文件**: `qml/components/Toast.qml:222-228`  
**问题描述**: `Toast.qml` 底部有一个覆盖整个 `toastRect` 的 `MouseArea`（用于点击关闭），它声明在 `toastRect` 之后，渲染层级更高。这导致 `toastRect` 内部的 `IconButton`（关闭按钮）无法接收点击事件。  
**影响范围**: Toast 的关闭按钮可能无法点击，用户只能等待自动消失。  
**修复建议**: 将外层 MouseArea 的 `z` 设为低于 IconButton，或给外层 MouseArea 添加 `z: -1`。

### M-11: SettingsPage ComboBox 语言切换绑定断裂

**文件**: `qml/pages/SettingsPage.qml:803-812`  
**问题描述**: `ComboBox` 的 `currentIndex` 绑定为 `SettingsController.language === "zh_CN" ? 0 : 1`，但在 `onActivated` 中执行 `currentIndex = index` 打破了绑定。如果 C++ 侧后续修改了语言设置，ComboBox 将不会反映实际语言。

### M-12: SettingsPage 自动保存 Switch 缺少防循环保护

**文件**: `qml/pages/SettingsPage.qml:953-956`  
**问题描述**: `autoSaveResult` 的 Switch 使用 `onCheckedChanged` 而非 `onToggled`，且没有 `updating` 防循环标志。当用户切换时可能产生绑定循环或信号风暴。同文件中的其他 Switch（如 `videoAutoPlaySwitch`）正确使用了 `onToggled` + `updating` 标志。  
**影响范围**: 自动保存设置开关，可能导致 QML 引擎绑定循环警告或 UI 抖动。  
**修复建议**: 改为 `onToggled` + `updating` 标志模式，与其他 Switch 保持一致。

### M-13: ShaderParamsPanel customPresets/customCategories 本地修改后绑定断裂

**文件**: `qml/components/ShaderParamsPanel.qml:29-30`, `qml/components/ShaderParamsPanel.qml:869-871`  
**问题描述**: `customCategories` 和 `customPresets` 初始绑定为 `UIStateController.getCustomCategories()` / `UIStateController.getCustomPresets()`。但在删除预设、删除类别、保存预设时，代码执行 `root.customPresets = presets`，打破了绑定。此后 C++ 侧的预设变更无法传播到 QML，且本地修改也未同步回 `UIStateController`。  
**影响范围**: 自定义预设和类别的增删改。用户在一个会话中创建的预设，在绑定断裂后不会被持久化到 C++ 侧。  
**修复建议**: 所有对 `customPresets`/`customCategories` 的修改应通过 `UIStateController` 的方法进行。

### M-14: ControlPanel displayMode 与 processingMode 不一致

**文件**: `qml/components/ControlPanel.qml:22-33`, `qml/components/ControlPanel.qml:170-172`  
**问题描述**: 控制面板的模式按钮只修改本地 `displayMode`，不修改 `UIStateController.processingMode`。这意味着用户在控制面板点击 "AI" 按钮后，面板显示 AI 参数，但实际处理模式仍为 Shader。MainPage 底部的模式按钮则正确修改了 `UIStateController.processingMode`。两处按钮行为不一致。  
**影响范围**: 用户在控制面板切换模式后点击发送，实际使用的是之前的模式参数，产生困惑。  
**修复建议**: 控制面板模式按钮也应修改 `UIStateController.processingMode`，或移除控制面板的模式切换功能。

### M-15: MainPage._getShaderParam 父链遍历脆弱

**文件**: `qml/pages/MainPage.qml:641-650`  
**问题描述**: `_getShaderParam` 通过遍历 `parent` 链查找 `objectName === "AppRoot"` 的对象来读取属性。这种方式极度脆弱：如果 MainPage 被嵌入到其他容器中（如 StackView 的中间层），父链中可能出现其他具有同名属性的对象，导致读到错误值。  
**影响范围**: Shader 参数传递和 AI 参数获取。组件层级变化可能导致参数读取失败或读到错误值。  
**修复建议**: 使用 `required property` 从上层组件显式传递参数，或使用 QML 的 `Binding` 对象。避免父链遍历。

### M-16: fullshader.frag 中 denoise/sharpness 的邻域采样也来自原始纹理

**文件**: `resources/shaders/fullshader.frag:84-95`, `resources/shaders/fullshader.frag:183-216`  
**问题描述**: 与 S-14 类似，`neighborColors` 数组从 `source` 纹理采样（原始颜色），但 denoise 和 sharpness 的处理对象是已经过 brightness/contrast 等调整的 `rgb`。中值滤波（denoise）基于原始颜色计算中值，然后与处理后的颜色混合；锐化（sharpness）基于原始颜色的局部方差计算边缘因子。两者都会导致处理结果与预期不符。  
**影响范围**: denoise + 其他颜色调整、sharpness + 其他颜色调整的组合使用。  
**修复建议**: 同 S-14，需要两遍渲染管线：第一遍渲染颜色调整到 FBO，第二遍从 FBO 采样做空间处理。

## 🟢 轻微 Bug（代码质量/潜在风险）

### L-01: ImagePreprocessor::extractTile() — 边界越界读取

**文件**: `src/core/inference/ImagePreprocessor.cpp:101-109`  
**问题描述**: `extractTile()` 从 `tileInfo.x, tileInfo.y` 位置提取区域。当 tile 在图像边缘时，`extractX + extractW` 可能超过图像宽度，`QImage::copy()` 会用黑色填充越界区域，不会崩溃但结果不符合预期（应该是镜像填充而非黑色填充）。  
**影响范围**: 边缘 tile 的填充区域为黑色而非镜像，可能轻微影响边缘推理质量。  
**修复建议**: 在 `extractTile()` 中对边界 tile 使用 `createPaddedImage()` 的镜像填充逻辑。

### L-02: ImagePostprocessor::mergeTiles() — 未实现

**文件**: `src/core/inference/ImagePostprocessor.cpp:76-84`  
**问题描述**: `mergeTiles()` 完全未实现，只输出警告并返回空 QImage。虽然当前 `processTiled()` 使用 `QPainter` 直接绘制到输出图像（不调用 `mergeTiles()`），但这个公共 API 的存在可能误导调用方。  
**影响范围**: 如果有代码调用 `mergeTiles()`，将得到空图像。当前无实际影响。  
**修复建议**: 实现 `mergeTiles()` 或删除该 API 并在头文件中移除声明。

### L-03: VideoResourceGuard::findStreamInfo() — totalFrames 估算依赖未初始化的 decCtx

**文件**: `src/core/video/VideoResourceGuard.cpp:151-153`  
**问题描述**: `findStreamInfo()` 中检查 `m_impl->decCtx` 是否非空来估算 `totalFrames`，但 `openDecoder()` 在 `findStreamInfo()` 之后才被调用（`initializeInput()` 的调用顺序是 `openInputFile → findStreamInfo → openDecoder`）。因此 `m_impl->decCtx` 在此处始终为 `nullptr`，`totalFrames` 的估算逻辑永远不会执行。  
**影响范围**: 当 `nb_frames` 为 0 时（某些视频格式），`totalFrames` 被硬编码为 1000，进度条不准确。  
**修复建议**: 将帧率估算逻辑移到 `openDecoder()` 之后，或在 `initializeInput()` 完成后重新计算 `totalFrames`。

### L-04: AIVideoProcessor::processInternal() — decFrame/encFrame 分配失败未处理

**文件**: `src/core/video/AIVideoProcessor.cpp:336-337`  
**问题描述**: 检查 `decFrame`/`encFrame`/`pkt`/`outPkt` 是否分配成功，但 if 块为空——什么都没做。后续代码直接使用这些可能为 `nullptr` 的指针，会导致崩溃。  
**影响范围**: 在内存不足时，FFmpeg 帧分配失败会导致空指针解引用崩溃。  
**修复建议**: 在 if 块中调用 `fail()` 并 return。

### L-05: SessionController::deleteAllSessions() — 逐个删除会话效率低且可能触发多次信号

**文件**: `src/controllers/SessionController.cpp:1834-1836`  
**问题描述**: 逐个调用 `m_sessionModel->deleteSession(sessionId)` 删除会话，每次删除都可能触发 `activeSessionChanged` 信号和会话切换逻辑，导致不必要的消息加载/保存操作。  
**影响范围**: 删除大量会话时性能差，可能导致 UI 闪烁。  
**修复建议**: 在 `SessionModel` 中添加批量删除方法，或先断开信号连接再批量删除。

### L-06: AIInferenceThread — m_worker 在 QThread::finished 时 deleteLater，但 stop() 可能在线程结束后访问

**文件**: `src/core/ai/AIInferenceWorker.cpp:462-503`  
**问题描述**: 构造函数中 `connect(m_thread, &QThread::finished, m_worker, &QObject::deleteLater)`，但 `stop()` 方法在 `m_thread->quit()` + `m_thread->wait()` 后仍然可能通过 `m_worker` 指针访问已标记为 `deleteLater` 的对象。
